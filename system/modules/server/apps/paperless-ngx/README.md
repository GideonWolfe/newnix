# Paperless-ngx

Native NixOS Paperless runs on **vm-app1** at <http://192.168.88.101:4232>.
It is LAN/VPN-only, with normal authentication enabled. No public DNS or Traefik
route is configured.

The current pinned nixpkgs provides **2.20.15**. The OCR settings here target that
version; review upstream migration notes before upgrading to a new major version.
The native module supplies Redis, a management CLI, and a local SQLite database.

## Storage

| Purpose | VM path | Backing storage |
| --- | --- | --- |
| Documents, OCR/archive PDFs and thumbnails | `/nas/tank/personal/docs` | NAS via the existing NFS mount |
| SQLite, index, classifier and application state | `/data/paperless` | Local ext4 |
| Incoming files | `/data/paperless/consume` | Local ext4; removed after ingestion |
| Metadata export for backups | `/data/paperless/export` | Local ext4 |

Paperless manages its normal media layout directly on the NAS. There are no
additional bind mounts or directory-preparation services. On mnemosyne:

```text
/tank/personal/docs/
└── documents/
   ├── originals/
   │   └── My Bank/Statements/2026/
   │       └── 2026-09-30 - September statement - 123.pdf
   ├── archive/
   │   └── My Bank/Statements/2026/
   │       └── 2026-09-30 - September statement - 123.pdf
   └── thumbnails/
```

These are ordinary files, not links into the VM or database blobs. Originals keep
their input format; archives are PDF/A with embedded OCR text where conversion
succeeds. Keep both branches: not every document can produce an archive PDF.
Thumbnails and Paperless's media lock also live on the NAS; keeping them local
is not worth maintaining a separate mount layout.

The naming rule is correspondent / document type / year / date-title-ID. Missing
correspondent/type levels are omitted. Editing metadata in Paperless updates the
real paths. If changing the global naming rule later, first back up the library,
then run `sudo paperless-manage document_renamer` to update existing documents.
Per-document Storage Paths in the UI override the global rule.

Tags, notes and custom fields remain database metadata unless explicitly included
in naming rules. The metadata backup below preserves them; the document folder
alone is not a complete replacement for the Paperless database.

### One-time NAS setup

Before deploying, create these directories **on mnemosyne**:

- `/tank/personal/docs`
- `/tank/infra/services/paperless/restic_backup`

Give both ownership **UID 315 (the VM's paperless user), GID 100 (users)** and
mode **2770**. Their parents must allow traversal. This avoids trying to chown
directories as root over root-squashed NFS. Paperless creates the document
subdirectories itself; local application directories are handled by NixOS.

Paperless runs as its dedicated user with supplementary `users` membership.
Setgid NAS directories and umask `0027` keep new files group-readable, not public.
Local application state stays private. Services wait for the local disk and NAS
before starting.

One pre-start command ensures the local data, inbox and export directories exist
with private permissions. This is needed because tmpfiles refuses to traverse
the `gideon`-owned `/data` into a directory owned by `paperless`; without it,
startup can fail with `PAPERLESS_CONSUMPTION_DIR is set but doesn't exist`.
The command does not touch NAS directories or recursively change file ownership.

Browse live document storage read-only. Import through the UI or inbox rather
than editing, renaming or adding files directly to the managed trees.

The docs folder is a normal directory within the existing `tank/personal`
dataset, so its current Sanoid snapshots and replication to soteria cover it.
No new dataset, NFS export or NAS rebuild is required. Stop Paperless before
detaching its storage; copies/snapshots are independently readable without it.

If the earlier split-mount configuration was already deployed, stop Paperless
and unmount its two old bind mounts, then move the existing `originals` and
`archive` directories under `docs/documents` before switching. This configuration
change does not move existing files.

## Initial setup and secrets

1. Create `secrets/secrets_paperless.yaml` with the structure below and SOPS-encrypt
   it yourself. The root encryption rules include vm-app1 and Gideon's GPG key.
   The encrypted file is intentionally not generated by this module.
2. Include the encrypted file and new module files in the deployment checkout,
   then deploy vm-app1 through the usual workflow. All new Nix files must be
   included in Git when using a Git-backed flake.
3. Open the LAN UI and sign in as **admin** using the configured password.
4. Upload a test document and check both its UI metadata and the NAS paths.
   Assign a correspondent, document type and title to make the directory layout
   useful. Matching rules/workflows can automate later imports.

```yaml
paperless:
  admin_pass: "STRONG_ADMIN_PASSWORD"
  restic_password: "SEPARATE_STRONG_BACKUP_ENCRYPTION_PASSWORD"
```

The per-secret declarations are in
[secrets/secrets_paperless.nix](secrets/secrets_paperless.nix); they do not override
other services' default SOPS files. Changing the admin secret restarts the
scheduler, whose native initialization updates the admin password. Keep the
Restic password safe: losing it makes encrypted backups unreadable.

The native web service generates its own persistent Django signing key under the
local data directory; it is included in backups. No additional secret-key or
database-password secret is needed for this SQLite configuration.

The consumption directory is private to Paperless and is not a network share.
Start with web uploads; scanner upload/sharing can be added separately. It is an
inbox, not an in-place library indexer: successfully consumed inputs disappear.
Office documents and email-file conversion require the optional Tika/Gotenberg
services, which are not enabled here.

## Backups and recovery

The daily `restic-backups-paperless` job first runs `paperless-exporter`.
The native exporter stops all four Paperless processes, creates a **data-only**
metadata export, and restarts them on success or failure. Workers have time to
finish in-flight OCR, so the backup can temporarily make the UI unavailable.
Restic's first pre-start command starts the one-shot exporter synchronously; a
failed export prevents the backup. Only that fixed systemctl command runs as
root, while the export and backup run as `paperless`. There is no separate
export timer or dependency that lets application restarts cancel the backup.

Restic then saves the export, the package version used to create it, and the
Django signing key to:

```text
/nas/tank/infra/services/paperless/restic_backup
```

It runs as `paperless`, using the shared NAS group, and retains 7 daily, 4 weekly
and 6 monthly snapshots. It does **not** copy a live SQLite database, regenerate
document copies, or back up caches/thumbnails. The NAS document trees and Restic
repository already have their own ZFS snapshot/replication policies.

**Restic metadata and NAS snapshots are not one atomic backup.** File moves and
deletions after an export can make a newer live library differ from that export.
Keep a corresponding NAS snapshot when making a recovery checkpoint. For a
self-contained migration/backup, use a full `document_exporter` run without
`--data-only` while Paperless is stopped, rather than relying on metadata alone.
The full exporter can use `--use-filename-format`, `--use-folder-prefix` and
`--split-manifest` to keep organized files and per-document JSON metadata.

For recovery:

1. Disable the backup timer and stop Paperless before restoring anything. Restore
   the metadata export/signing key and the corresponding NAS document trees,
   retaining the same configured paths and appropriate ownership.
2. Use the Paperless version recorded in the export's `paperless-version.txt`.
   Prepare a fresh, migrated but otherwise empty SQLite database; do not import
   over the existing database or let startup seed an admin user first.
3. Run `sudo paperless-manage document_importer /data/paperless/export --data-only`.
   This leaves document files in place and restores their database references.
4. Rebuild thumbnails and the search index with `paperless-manage document_thumbnails`
   and `paperless-manage document_index reindex`, running as root or `paperless`.
   Run `paperless-manage document_sanity_checker` before restarting the services
   and backup timer. Missing files indicate an incomplete/mismatched restore.

See the upstream [file naming](https://docs.paperless-ngx.com/advanced_usage/#file-name-handling)
and [export/import](https://docs.paperless-ngx.com/administration/#exporter)
documentation for details.
